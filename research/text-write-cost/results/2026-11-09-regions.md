## H3: text changes as history (claim) records

Verdict: **refuted**, but not for the reason the hypothesis names. The mechanics work; the key
order does not.

What holds (code):

- Many records per revision, not one. A claim record is keyed
  `history_key(version, entity, attribute, value)` (`dialog-artifacts/src/key/history.rs`,
  `history_key`; `history/record.rs`, `Record::key`). `write_instructions`
  (`dialog-artifacts/src/tree.rs`) buffers one record per distinct `(e, a, v)` per batch and
  folds collisions (`buffer_record`, `fold_record`). So N distinct changes in one commit are N
  records under one signed revision. Caveat: two identical change bytes on the same
  `(doc, attribute)` in one batch fold into one record, so the value must be unique (carry the
  sequence).
- Screening ignores them if they cover nothing. `merge::screen_record` only scans when the key
  is under `HISTORY_KEY_TAG` and `supersedes` is non-empty; otherwise the record just appends.
  `Record::coverage_entry` returns `None` for an empty cause, so no coverage-region entry and
  graft repair (`pull.rs`, coverage loop after the stitch) never sees it. `screen_data` never
  sees history keys (`merge::history_scope` vs `merge::data_scope`). So screening, coverage and
  merge need no change for records with empty `supersedes`.
- A record without a data-region index entry is not reachable through instructions:
  `Instruction::Assert` always writes the three orderings, and `Retract` of an absent fact is a
  no-op with no record (`tree.rs`, Retract arm). It is reachable through the machinery path:
  `Commit::with_entries` (`dialog-repository/src/repository/branch/commit.rs`, `pub(crate)`)
  feeds raw `(Key, State<Datum>)` into `batch.record`, and "machinery entries count as changes",
  so a commit with only such entries mints a revision. `Record::into_entry` builds the entry.
  Inference: a same-batch assert+retract at tree level folds to a genesis Retract record with
  no index entries, but `repository/staged.rs::squash` drops the cancelled assert before it
  reaches the tree, so this is not a usable path (not verified by a test).

Why refuted (code + inference):

- History keys are `tag ‖ origin ‖ edition ‖ entity ‖ attribute ‖ value`. One document's
  changes are scattered across every `(origin, edition)` span that touched it, interleaved with
  every other document's and every fact's records. The only lookup is
  `history_claim_range(version, of, the)`, which needs the version first. Opening a document
  therefore needs a separate index from document to versions (which brings back a data-region
  entry per change or per revision) and then one range read per revision. This fails H4 and the
  "partial replica holds one document whole" scope.
- `Download::operational` (`branch/download.rs`) deliberately skips history and coverage as
  "the only regions that grow with every edit", and history hydrates on demand. Text living
  there is the opposite of what partial replication is tuned for.
- Inference: text records would also appear in any history/claim query on the document entity
  (conflict walks, log-style queries), mixing operations with fact lineage.

## H1 scope: a dedicated text region `tag ‖ document ‖ origin ‖ sequence → change`

How regions are defined today (code): one leading tag byte per region, constants spread over
`dialog-artifacts/src/key/`: `ENTITY 0`, `ATTRIBUTE 1`, `VALUE 2`, `HISTORY 3`, `BLOB 4`,
`COVERAGE 5`, `CONTEXT 6` (`key/context.rs`: `tag 6 ‖ origin`, 33 bytes, value a `Datum` with
only `blob` set). There is no registry: each consumer matches on tags. `Key::schema`
(`key.rs`) gives EAV/AEV/VAE/BLOB columnar schemas and treats every other tag as one opaque
column; `varkey::parse_key_layout` parses unknown tags as EAV.

Can a commit write region entries without claim records? **Yes, already** (code): the context
region and blob-index entries do exactly this through `Commit::with_entries` and
`RecordEntries` riding `batch.record` beside the revision record; no instruction, no claim
record, one seal. Only the API is `pub(crate)`.

What adding tag 7 touches:

| Area | File / function | Change |
|---|---|---|
| Key layout | new `key/text.rs`, exports in `key.rs` | tag constant, key builder/reader, doc range helper (context.rs is the template) |
| Commit | `branch/commit.rs` (`with_entries`), transaction API | public way to stage text entries; commit with only text entries already mints |
| Merge, replay direction | `branch/pull.rs` (scenario 5a, ~line 1052) | **today diffs only `history_scope` + `data_scope`: tag 7 entries of our side are silently dropped**; add a third, unscreened `text_scope` diff |
| Merge, screened direction | `branch/pull.rs` (~line 1209) | same: upstream's tag 7 entries silently dropped; add `text_scope` |
| Lost-race merge | `branch/merge.rs` (~line 151) | same allow-list, same fix |
| Graft merge | `branch/pull.rs` (~line 744) | none: `full_scope` partitions and stitches whole subtrees; contested spans go through `screen_data`, which passes unversioned entries (unique keys, so no contests) |
| Scopes | `merge.rs` | `text_scope()`, maybe a per-document span |
| Push | `branch/push.rs` | none for nodes (full-tree `TreeDifference`); `spill::shipment_ref` must exclude tag 7 like COVERAGE/CONTEXT, or an opaque key that happens to parse as EAV with a spill tail is read as a block reference |
| Value-encoding migration | `tree/rekey.rs::rekey` | must pass tag 7 through like BLOB/CONTEXT; today `parse_key` fails on it and the rewrite errors |
| Inspect | `inspect.rs` | label |
| Partial replication | `branch/download.rs` | `Download::within(scope)` already materializes arbitrary key ranges; add a per-document scope helper; `operational()` stays as is |
| Verification | none today | text entries are covered only by the root hash; the origin in the key is not bound to the signer |
| CHANGELOG / compat | `CHANGELOG.md` | storage and sync change, breaking (`feat!`) |

Size estimate (inference): 8 to 10 files; about 350 to 450 lines of production code, about 400
to 600 lines of tests (commit writes region without claims; every merge direction carries it:
graft, replay, screened, lost-race; push ships it; migration keeps it; one document downloads
whole).

Riskiest part (inference): the merge paths select regions by allow-list. Any replica, or code
path, that does not list tag 7 silently drops text on the replay and screened directions, and
the merged head's watermark still claims those revisions as seen, so nothing re-sends them.
That makes mixed-release networks lose text without an error. It needs a format gate (manifest
or head marker, as the context region used) before any older replica can merge such trees.
Second risk: authenticity. Adopt-by-root and graft never enumerate entries, so per-entry
origin checks on pull are not free; either sign changes (about 64 bytes each) or accept that
the origin is attribution only, as the profile field is today.

## H4 / E3: one document replicated whole among many

How partial replicas fetch today (code): a pull adopts by root; nodes hydrate lazily as reads
touch them (the store falls through to the remote, `RemoteFallback`). `Branch::download` /
`Pull::download().within(ranges)` materializes chosen key ranges eagerly. So "fetch
`tag ‖ document` whole" is a range read or a scoped download, no new mechanism.

Method: `examples/text_region_reads.rs` builds the production `ArtifactTree` (real key and
`State<Datum>` types, default manifest). Per document: 500 changes of 20 to 50 bytes from 3
origins, keyed `7 ‖ doc(16, hashed) ‖ origin(32) ‖ seq(8)`, value a `Datum` with the bytes in
`blob`; plus real facts from `generate_data` (about 45 entries per document over the three
orderings). The tree is built canonically, then one document's range is streamed through a
store with no node cache, counting every load, its bytes, and the entries in fetched leaves
outside the document's prefix ("foreign"). Four documents sampled per size.

```sh
cargo run --release -p dialog-artifacts --features helpers --example text_region_reads
# TEXT_REGION_DOCUMENTS=1,100,1000,10000 to choose sizes
```

| docs | tree entries | tree MiB | height | blocks per doc (range) | bytes per doc (range, avg) | foreign entries fetched (range) |
|---|---|---|---|---|---|---|
| 1 | 542 | 0.09 | 2 | 5 | 94 KB (whole tree) | 42 |
| 100 | 54 497 | 8.9 | 3 | 4 to 6 | 129 to 269 KB (193 KB) | 139 to 969 |
| 1 000 | 544 997 | 89 | 3 | 4 to 7 | 140 to 333 KB (219 KB) | 242 to 1 132 |
| 10 000 | 5 449 997 | 893 | 3 | 5 to 7 | 176 to 335 KB (260 KB) | 136 to 567 |

Verdict: **confirmed**. Reading one document from cold costs 4 to 7 blocks and 130 to 335 KB at
every size from 100 to 10 000 documents while the tree grows 100 times; height stays 3. The
overhead beyond the document is its two boundary leaves (on average about one other document's
worth of entries) plus the root-to-leaf path, not a share of the total.

Side findings for E1 (measured): a stored entry costs about 172 bytes (893 MiB / 5.45 M
entries) for a 20 to 50 byte change, about 5 times the payload; a document's own 500 changes
occupy about 85 KB of leaves for 17.5 KB of change bytes. Leaves are about 47 KB, so one
document spans about 2 leaves. Inference: most of that per-entry cost is the opaque 57-byte key
column (no per-component schema for unknown tags) and the CBOR `Datum` wrapper; a text-specific
value type and key schema would cut it, which matters for H1's 2x criterion.

## Notes and docs the code contradicts

- `notes/version-control.md` (measured costs) says clustering the revision record like the log
  is "blocked on variable-length keys: a full origin plus edition does not fit the fixed
  order-preserving key head". Keys are variable-length now (`key/varkey.rs`;
  `history_claim_range` says "every component is lossless now").
- The module doc of `dialog-artifacts/src/key/history.rs` still describes the fixed 202-byte,
  head-plus-Blake3 layout; the code builds variable-length keys.
- The module doc of `dialog-artifacts/src/key/context.rs` says the head carries "the most
  recently active of those entries and a digest of the rest"; the notes, `history/region.rs` and
  the `Revision` struct (`dialog-capability/src/identity/revision.rs`) carry no entries and no
  digest.
- The notes say "Same-batch assert+retract cancels to nothing". True for the indexes; at tree
  level the record fold appears to leave a genesis Retract record in the log (inference from
  `write_instructions`, not tested), and the repository's `squash` keeps the retraction when the
  line holds the value.
- The notes' region diagram lists data, history and coverage only; the blob (4) and context (6)
  regions are missing from it.
