# 2026-11-12: a record's identity as a merkle reference

The maintainer decided that a record is referenced canonically by its merkle
reference (`rust/merkle-reference`, version 2). Code:
`rust/dialog-repository/examples/record_spike/merkle.rs`, run by
`record_spike measure`; datasets, build and container as
[the first sitting](2026-11-11-spike.md) (revisions-4000-11, versions written
as nested records; tonk-bindings).

## The reference

The spec's rule for a struct, applied to a record: a map under `record:` from
each attribute, its relation as a `symbol:`, to its value's reference, or to
the `set:` of its values' references when it holds several. A nested record's
value is its own reference. Every scalar keeps the reference dialog already
gives it (`Value::reference`, `dialog-corpus/src/identity.rs`): a number by
its one-band encoding, so `3` and `3.0` are one value here too.

Nothing of the bytes' layout enters it. Names inline, in a header, or in a
buffer's table give one reference, and so do a nested record held inline and
one held apart: the spec's partition independence.

## It is the canonical form's identity

Over 200,000 generated records (155,200 distinct; up to six pairs, nested to
depth two, sets, every value type): equal references exactly when equal
canonical bytes, both ways.

## What it costs

ns a record, seven rounds interleaved, run twice (the second shown; the first
within 3% at every median).

| record | identity | min | median | max | ÷ BLAKE3 of the bytes |
|---|---|--:|--:|--:|--:|
| revision record | BLAKE3 of its canonical bytes | 576 | 634 | 708 | 1.0 |
| | merkle reference, every part hashed | 5,295 | 5,834 | 6,792 | 9.2 |
| | merkle reference, parts' references kept | 2,035 | 2,190 | 2,247 | 3.5 |
| view bindings | BLAKE3 of its canonical bytes | 728 | 778 | 821 | 1.0 |
| | merkle reference, every part hashed | 13,724 | 14,238 | 15,088 | 18.3 |
| | merkle reference, parts' references kept | 4,914 | 5,303 | 5,788 | 6.8 |

"Kept" is a buffer holding each attribute's and each scalar value's reference
beside its token, as the single-file archive could: only the maps and sets
are hashed. A revision record with versions as nested records holds a map per
version, which is most of what is left; with versions as bytes it would hold
none.

## What follows

- Two canonical byte strings are equal exactly when their references are, so
  in memory, between canonical bytes, `Eq` and `Hash` over the bytes agree
  with identity and cost a tenth as much. The reference is computed where
  identity leaves memory or crosses buffers: a rule's identity, a signature,
  a spilled value's name, two views from two buffers.
- A buffer that keeps its parts' references compares views from two buffers
  without realizing either, at about a third of the cost of hashing all.
- A signature over a record's reference holds whatever layout carries it.
