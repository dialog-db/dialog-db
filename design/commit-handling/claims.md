# A branch commit is refused when the head has moved: claims

| claim | kind | backing | status |
|---|---|---|---|
| A branch commit publishes its revision by compare-and-set of the head cell against the head it was built on; if the head moved, the publish fails with `PublishError::VersionMismatch` | fact | `rust/dialog-repository/src/repository/branch/commit.rs` on main `4fd67af` (`perform_on_branch`: `branch.revision.checkpoint()`, `head.publish`) | holds |
| A commit whose writes change nothing re-reads the head and fails with the same `VersionMismatch` if it moved | fact | `commit.rs`, the `Outcome::Unchanged` arm | holds |
| After a lost race a staged batch is stale, and recovery is to run the transaction again on the fresh head; dialog leaves that to the caller | fact | `rust/dialog-repository/src/repository/branch/transaction/batch.rs`, the doc of `TransactionBatch` | holds |
| Blocks of a staged batch that is never published stay in the archive, unreachable | fact | the same doc of `TransactionBatch` | holds |
| Within one environment, commits and pulls of one branch take turns under a writer lock | fact | `commit.rs` (`branch.writer().lock()`) | holds |
| A commit can ask to `merge()`: on a lost race its minted revision is kept and a merge of it with the winning head is published; a value both set is elected by version when read | fact | `commit.rs` (`Commit::merge`, `merge_with_winner`) | holds |
| The publish checks only whether the head cell changed, not whether what the transaction read was changed by whoever moved it | fact (was a hypothesis, confirmed 2026-11-10) | `TransactionBatch` publish in `transaction/batch.rs` and `perform_on_branch` in `commit.rs` go from mint to `head.publish` with no other comparison; `ReadObservation` is the key of the settlement memo (`staged.rs`, `take_settlement`) | holds |
| Tonk's reactor refreshes and runs a refused commit again up to four times, recognising the refusal by the rendered text "Version mismatch" | fact | tonk `bfb2d72`, `rust/dialog-reactor/src/transaction.rs` (`COMMIT_RETRY_LIMIT`, `is_head_moved`) | holds |
| Tonk's evaluate route runs a refused commit again up to four tries, except when the request named an expected revision, where it answers with a revision conflict and does not run again | fact | tonk `bfb2d72`, `rust/tonk-worker/src/router/evaluate.rs` (`EVALUATE_RETRY_LIMIT`, `revision_conflict`) | holds |
| In tonk the only thing that races a commit is sync, and one retry settles it in practice | hypothesis | said by a comment in `rust/dialog-reactor/src/transaction.rs`; confirmed or refuted by counting "reactor commit raced (attempt N)" log lines on a running app, and by listing what else writes the head cell (another tab, a worker) | open |
| A refused commit gives a UI application no good strategy for handling it | opinion | the maintainer, 2026-11-10 | - |
| An approach inspired by Software Transactional Memory should handle commits | opinion | the maintainer, 2026-11-10 | which part of it is meant is not yet said |
| Software Transactional Memory answers a conflict by discarding the attempt and running the body again, so adopting it moves the refusal from the caller into the runtime and does not remove it | hypothesis | the agent, 2026-11-10; refuted if the maintainer means a part of it that never runs the body again, or if the run-again is acceptable to a UI when the runtime does it | refuted 2026-11-10: the maintainer wants the running again, done by dialog; the objection is to callers doing it |
| Tonk's command line publishes a write with no `merge()` and no second try, and reports a refusal as "commit failed" with the error's text | fact | tonk `bfb2d72`, `rust/tonk-cli/src/eval.rs` (`txn.commit().publish()`) | holds |
| Tonk's command line pulls before a write and pushes after it; a push refused because the upstream moved is answered by pull (merging both sides' facts) and push again, up to five times | fact | tonk `bfb2d72`, `rust/tonk-cli/src/auto_sync.rs` (`pull_before`, `push_after`, `PUSH_ATTEMPTS`) | holds |
| In the web app a refused commit shows as an error in the console, or in the interface if the application's author handled it | fact, as reported | the maintainer, 2026-11-10; no incident or log linked | holds as a report |
| Two agents sharing a branch through the command line are often refused, and refused again when they try again | fact, as reported | the maintainer, 2026-11-10; no transcript linked | holds as a report |
| Agents write from a query that may be stale without considering that it may be | fact, as reported | the maintainer, 2026-11-10 | holds as a report |
| Ideally a commit never fails: it is given an operation dialog can run again on the latest state, and that considers the latest state | opinion | the maintainer, 2026-11-10 | a remedy; "never fails" and "considers the latest state" are not yet reconciled |
| The refusals the agents met are the local publish's (two processes on one replica's storage), not the push's | hypothesis | confirmed by an agent transcript showing "commit failed: ... Version mismatch"; refuted by one showing the push's non-fast-forward warning, or by each agent having its own replica | open |
| The web app's errors come from a commit path that does not run again, not from the reactor losing four tries | hypothesis | confirmed by naming the path (an application's own `publish`) or refuted by "reactor commit raced (attempt 4)" in a console log | open |
| Candidate problem 1: the head moving reaches every caller as the commit's error, though nothing in the application's terms answers it | hypothesis | the agent, 2026-11-10 | accepted by the maintainer, 2026-11-10 |
| Candidate problem 2: a caller whose round of reading, deciding and writing is longer than the gap between other writers' commits loses again when it runs again | hypothesis | the agent, 2026-11-10; confirmed by timing an agent's round against the other agent's commit interval | accepted by the maintainer from experience, 2026-11-10; not measured |
| Candidate problem 3: a write decided from a read is applied without the read being looked at again; the head check neither implies it (it refuses when nothing read changed) nor catches it (a read from an earlier invocation is unknown to the commit) | hypothesis | the agent, 2026-11-10; the first half rests on the open hypothesis above that the publish checks only the head cell; the second is shown by a test: query in one invocation, change the result from another, write from the first's result, and see the commit accepted | restated by the maintainer, 2026-11-10 (next row); what is left of it is kind 4 in the journal's table, a scope question |
| An agent's decision is made outside dialog, between invocations, so no operation dialog can run again holds it | hypothesis | the agent, 2026-11-10; refuted if agents can state their writes as a document whose queries carry the decision (the evaluate document already holds queries and writes together) | refuted 2026-11-10 as far as the agent states the change as a command; a query made in an earlier invocation stays outside |
| A correct loop for running a refused commit again is not obvious, and applications get it wrong | opinion, with evidence | the maintainer, 2026-11-10; consistent with tonk `bfb2d72`, where three callers handle the refusal three ways (reactor, evaluate route, command line; rows above) | accepted as problem 3 |
| A transaction can hold commands: a dispatched claim is a transient fact, inductive rules fire on it at commit against the transaction's view, their writes join the commit, the command is not stored | fact | `rust/dialog-repository/src/repository/branch/transaction.rs` on main `4fd67af` (`Transaction::dispatch`, `Transaction::commit`) | holds |
| Marking a todo done should be a command and a rule; the rule reads what it needs when it runs and writes accordingly, only if the todo still exists say | opinion | the maintainer, 2026-11-10 | - |
| Approach: capture the reads and writes a commit performed; with no overlap with what moved the head, apply it without running again; with overlap, assert the command again over the latest revision | opinion (a proposal) | the maintainer, 2026-11-10 | recorded for Direction; not examined |
| Dialog doing the work again answers the three accepted problems by itself; capturing reads and writes answers none of them alone, and what it adds is either a saved cost or telling apart the transactions dialog cannot do again | hypothesis | the agent, 2026-11-10; refuted by a problem the maintainer names that only the capture answers; the saved cost would be confirmed by measuring a command transaction run again against the same one applied without running | open |
| A commit applied or run again on the latest head still publishes by compare-and-set and can lose again, so "never fails" rests on something that bounds the loop, which the proposal does not name | hypothesis | the agent, 2026-11-10; refuted if all writers of a head cell take turns (the writer lock is per environment; two processes on one storage share only the cell), or by naming the bound | open |
| When a command's rule finds nothing to do, the agent or person that asserted it needs to learn so | hypothesis | the agent, 2026-11-10; asked and not answered; tonk's convention of outcomes as facts (`commands-not-routes` skill) may already be the answer | open |
