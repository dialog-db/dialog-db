# A replica cannot read or write what it held once a pull moves its head: claims

| claim | kind | backing | status |
|---|---|---|---|
| A pull that adopts an upstream head by root reads none of its tree: a fast-forward, a rival merge settled, a reset brought forward | fact | `rust/dialog-repository/src/repository/branch/pull.rs` (`merge_upstream`, the arms that return `Merged` with `new_revision: upstream_revision`); `it_adopts_an_upstream_head_without_reading_its_novelty` asserts zero block reads | holds |
| A read that misses a block locally fetches it from the subject's routes, mid-read, and keeps it | fact | `nodes::Read` answered by the peer (CHANGELOG, "A tree asks its environment for nodes"); `it_reads_what_it_held_after_adopting_a_head_another_device_moved` counts the `Hydrate` | holds |
| After such a pull, a replica's read of a fact it had read from its own blocks fetches a block when another replica changed that fact's leaf | fact | `it_reads_what_it_held_after_adopting_a_head_another_device_moved` with the follow disabled: 1 hydration where 0 are expected | holds |
| A write reads the leaves it writes to: the fact's leaf in the entity and attribute orders, and its history leaf | fact | probe on the topic's branch, 2026-11-10 (journal): an append to a fact the replica had read through one order fetched one attribute-order leaf (key tag 1) and one history leaf (tag 3); an append to an entity never read fetched its entity-order leaf (tag 0) | holds for an append under `Pick::All` in a tree of one index level; not probed for other picks or deeper trees |
| After such a pull, a replica's write to a fact it had already written fetches blocks again | fact | `it_writes_where_it_wrote_after_adopting_a_head_another_device_moved` with the follow disabled: 2 hydrations where 0 are expected | holds |
| A replica's first write to a fact it only read fetches the leaves of the orders it never read that fact through, with or without any change to pull | fact | the same probe: 2 to 3 hydrations on the first append, both ways | holds |
| A replica's later reads and writes of the same keys fetch nothing until the next adopted head changes those leaves | fact | the same tests: the second read and the second write count 0 hydrations | holds |
| A commit that lands while a pull is prepared makes the pull's publish fail with `PublishError::VersionMismatch`, the head stays where the commit put it, and the caller pulls again | fact | `land` in `pull.rs` ("A head moved by anything else fails the pull ... the caller refreshes and pulls again"); `it_keeps_a_commit_made_while_a_pull_followed_a_moved_head` | holds |
| Tonk's subscriptions fetch what their queries miss after a head moves, because it polls every subscription of the branch again once a pull changed the tree | fact | tonk `rust/dialog-reactor/src/pull.rs` (`cached.poll(env)` after `prepared.commit`) | holds |
| Tonk pulls spaces no page is showing: every space opened since its service worker started, in any tab | fact | tonk `rust/tonk-worker/src/router/sync.rs` (`drain_sync`, `watch_open_repos` over `Reactor::spaces`); tonk-team BUG-307 | holds, from reading the code; not measured |
| The reported slow load is this problem | hypothesis | confirmed if tonk's browser build, on a dialog that brings held keys along, renders the page of the reproduction with no fetch after the pull; refuted if it still fetches, or if the device's stored blocks were evicted by the browser | open: reproduced in tonk at dialog 0.4.0-rc.7 without the change; not run with it, tonk is two breaking releases behind main |
| The slow reactions to edits and the pulsing dot are this problem | hypothesis | confirmed if a tonk trace shows a commit waiting on a `Hydrate` after a pull, and the dot's state following it; refuted if the dot is driven by something else | open: the write half is shown in dialog, nothing was traced in tonk |
| Tonk already fetches before the head moves for the profile, access and account branches, by a download of the adopted revision it runs between `prepare` and `commit` | fact | tonk `rust/dialog-reactor/src/pull.rs` (`download`, `operational`; "a head adopted by reference with blocks still remote bricks the next boot") | holds |
| That opt-in was missed at least once: a caller pulled the account branch as it would a space's, and the profile stopped opening | fact | the same file: "The profile's own repository ... whoever pulls it, the pull downloads what it adopts"; tonk test `it_downloads_the_account_whoever_pulls_it` | holds |
| A walk of the held tree and the adopted tree in step, reading an adopted node only where its keys meet a leaf the replica holds, makes every key read from the replica's blocks before readable from them after | fact | `PersistentTree::follow` and its tests in `rust/dialog-search-tree/src/follow.rs` on the topic's branch | holds for the trees tested: two levels, appended, rewritten and interleaved keys |
| That walk's cost follows what changed in what the replica holds, not the size of the change | hypothesis | confirmed if the Replication gate's scenarios show a pull's fetches bounded by the held paths as upstream churn grows elsewhere; `it_brings_along_what_the_replica_read_and_nothing_else` shows it for one shape (fetched no more than the path read, with 2000 keys added elsewhere) | open: one shape, gates not run |
| Fetching everything by which two heads differ fetched 44 blocks where the page's query needed 7 | fact | tonk test of the withdrawn change (tonk `6fc0474`), 2026-11-10: every index order and history | holds |
| A slow link and a writer that commits continuously cannot starve a pull, because what one attempt fetched the next finds held | hypothesis | confirmed if a pull retried after a lost publish counts no `Hydrate` for the nodes the first attempt followed to; refuted if a retry fetches them again | open |
| A re-prepare inside `land`, under the branch's write lock, can now fetch: the follow runs in `prepare_upstream`, which `land` calls again when an earlier upstream of the same pull landed first | hypothesis | confirmed if a pull from two upstreams, the second re-prepared, counts a `Hydrate` while the writer lock is held; refuted if the re-merged head adds no node that meets a held leaf | open; only a branch with more than one upstream can reach it |
| The application should never wait on the network for what the device already showed, at the cost of showing a head that is behind | opinion | the maintainer, 2026-11-10: "you may be behind but application is always active" | - |
| Only what is needed to answer queries should be replicated, not every change | opinion | the maintainer, 2026-11-10 | - |
