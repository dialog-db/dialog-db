| DBSP treats a change as a weighted row and derives the incremental form of a query; CouchDB keeps reductions in the inner nodes of its view B-tree; Noria keeps state only for keys that are read | fact | Budiu and others, "DBSP: Automatic Incremental View Maintenance for Rich Query Languages", VLDB 2023; CouchDB's `couch_btree`; Gjengset and others, "Noria", OSDI 2018 | holds; cited from the papers' abstracts and the agent's recall, not re-read in full for this note |

| one poll of a subscription returns a change, the rows that started holding and the rows that stopped, not the whole answer | fact | `Delta { asserted, retracted }`, `dialog-repository/src/repository/branch/subscription.rs` 371-377; [subscriptions-as-built.md](subscriptions-as-built.md) §1 | holds |
| a subscription keeps its whole last answer as a flat list and nothing for a rule, a premise or a group; it learns a row stopped holding only by deriving the touched entity again and comparing | fact | the same file 388-430 and 1309-1330; [subscriptions-as-built.md](subscriptions-as-built.md) §2, §4 | holds; so no signed row of a rule's body exists anywhere today, which the agent's hypothesis of folding the changes needs |

| the one state a subscription keeps across polls beyond its answer is the fixpoint continuation of a recursive concept | fact | [subscriptions-as-built.md](subscriptions-as-built.md) §6, `fixpoint.rs` 1727 | holds; the only precedent for per-subscription operator state |
| on the page, tonk applies a change to a kept copy of every row and then folds, serializes and renders every binding again, so one changed fact costs the rows on the page | fact, read | [tonk-as-built.md](tonk-as-built.md) §2.5, `rust/tonk-display/src/element.rs` 843-883, `fold.rs` 84-145 | holds; not measured in tonk either |
| neither dialog nor tonk's planner aggregates anything today: a count is an element's script over rows, and a list is folded on the page | fact, read | [tonk-as-built.md](tonk-as-built.md) §4 | holds |
| a list of N nested views is N subscriptions of the entity, each checked on every write | fact, read; the count inferred | [tonk-as-built.md](tonk-as-built.md) §6; "a 200-row list opens the same three queries 200 times", `tonk-host/src/stream.rs` 4-9 | holds |
| a folding query's subscription can be a subscription of its inner query with a state for each group beside it, changed by what the inner poll reports, at the cost of the change and with nothing new asked of the engine's maintenance or of storage | hypothesis | the agent's, in [direction.md](direction.md), with what confirms and refutes it. | systems that fold changes sort a fold by what a retraction asks: `count`, `sum`, `avg` keep a number or two for a group and pay a step; a set of values keeps a count for each value; `min` and `max` need the group's values or the group read again | fact, read | [literature.md](literature.md) A2, A5, A6, A10: Gray and others 1997; DBSP and Feldera's cost table; Noria; Materialize. | a float `sum` folded from changes can differ from one folded from the rows, so two replicas with the same facts could show different totals | hypothesis | float addition has no exact inverse; dialog sums floats in `f64` (`rust/dialog-query/src/reduce.rs` 459-500); Feldera treats a float sum as not linear. Confirmed by a test that adds and retracts floats in two orders and compares with the fold of the rows; refuted if the totals are bit-equal | open |

| applying a batch of changes to a count or an integer sum gives the same result in any order | fact, read | Olteanu, "Recent Increments in IVM" (2024), via [literature.md](literature.md) A7 | holds; it is why a merge's changes need no ordering for these folds |
