# Claims: large transactions

| claim | kind | backing | status |
|---|---|---|---|
| The MusicBrainz replay (2,000 commits, 4.47 M facts) wrote 2,883,182 node versions, about 1,440 a commit | fact | `breakdown` of the replay's file, research/single-file-format journal, 2026-11-07 and 2026-11-08 | holds |
| The tree such a replay leaves is about 53,000 nodes (53,201 at ~1,250 commits) | fact | `live_breakdown`, research/single-file-format journal, "MusicBrainz against its source" | holds for that point of the replay |
| A node's buffer flushes past 256 ops (the manifest's branch factor) or 64 KiB of op weight (its `max_segment`) | fact | `op_buf_size`, `op_buf_bytes` in `rust/dialog-search-tree/src/hitchhiker.rs` | holds |
| A flush lifts the child it descends into to a transient node once per commit, edits it in place, and encodes it once, at persist; children nothing descends into pass through without a decode | fact | `enqueue`, `lift_child` in `rust/dialog-search-tree/src/hitchhiker.rs` | holds |
| A commit applies its whole instruction stream to the buffered tree before persisting anything | fact | `rust/dialog-repository/src/repository/branch/commit.rs`, the comment before `ArchiveDelta::zero()` | holds |
| `branch.import` makes an artifact stream one commit; `dialog-csv`'s `CsvImporter` is such a stream | fact | `rust/dialog-repository/src/repository/branch/import.rs`, `rust/dialog-csv/src/importer.rs` | holds |
| A canonicalized commit gives the history-independent tree, whatever the order its facts arrived in | fact | the doc of `Commit::canonicalize`, `rust/dialog-repository/src/repository/branch/commit.rs` | holds |
| A commit that fits in the root's buffer persists a handful of nodes; one larger than the buffers persists about one node per distinct leaf its ops reach | hypothesis | confirmed if nodes persisted per commit, on one base tree, stay near the tree's depth for commits of 10 and 100 facts and grow with the leaves touched for 1,000 and 10,000 | open |
| The same facts in fewer commits write fewer node versions and take less time; one commit writes about the final tree once | hypothesis | the MusicBrainz facts as 1, 10, 100 and 2,000 commits: node versions written, time, file size | refuted past a point: as 100 commits, 1.01 M node versions, 2,616 s of commits, 531 MiB, peak commit heap 4.9 GiB, against 2.88 M, 6,833 s and 1,005 MiB as 2,000 (format 10); as 10, a second commit ran over two hours; as one, out of memory (`file_archive_bench`, `DIALOG_BENCH_GROUP`, 2026-11-08) |
| A one-commit import of the MusicBrainz facts holds gigabytes at its peak (the final tree as blocks is about 53,000 × 71 KB, 3.7 GB) | fact (in part) | the replay's facts as one commit (`DIALOG_BENCH_GROUP=2000`, `file_archive_bench`, 2026-11-08) was killed by the kernel after 116 s at 13.6 GiB of anonymous memory on a 15 GiB machine; the bench itself holds about 5.7 GiB (the 2,000-commit run's peak, the log and its instructions included), so the commit held over 8 GiB, still growing, when it died. Not yet measured through `branch.import`, which streams its facts | confirmed that one commit of this size does not fit; how much it holds is open |
| With buffers about as large as a node's fan-out (256 against ~185 children a level below the root), a flush moves one or two ops into each child it rewrites | hypothesis | ops moved per child rewrite, counted over the replay; the `FlushTrigger::Capacity` doc says the same of scattered keys | open |
| Sealing a commit applies the ops its buffers sent toward leaves one canonical edit at a time (`replay_ops`: an insert or delete each, descending, editing the leaf and reshaping the path), except into an empty tree, which is built bottom-up in one pass (`plant`) | fact | `replay_ops` in `rust/dialog-search-tree/src/hitchhiker.rs` | holds |
| The replay's facts as 10 commits (about 447,000 facts each): the first commit, into an empty tree, finished; the second ran for over two hours at full CPU on one thread, holding 6.8 GB, and was stopped. Five stack samples were all in `BufferedBatch::seal` → `HitchhikerTree::settle` → `replay_ops` → `TransientTree::insert` → `Edit::apply`, in `PieceSummary::build` (`weight_paced_cut`, `Hashed::hash`) or `reshape_path` | fact | `file_archive_bench` with `DIALOG_BENCH_GROUP=200`, 2026-11-08; gdb samples | holds |
| In the 2,000-commit replay, 25 minutes in (about 2,234 facts a commit), ten stack samples of the busy thread were all in `BufferedBatch::seal` → `replay_ops` → `TransientTree::insert` → `Edit::apply` (piece summaries, `reshape_path`, `carry_novelty`, `merge_forced_index_runs`), none in the archive | fact | gdb, ten samples within one minute (so correlated), `file_archive_bench` at 9db30658, 2026-11-08 | holds for that minute only: over the whole replay's 6,562 s of commits, the archive's timers account for about 4,125 s (appends 2,975, of which splitting nodes into rows 2,507; reads building blocks and decoding rows 1,150, which a store serving nodes in place would skip), leaving about 2,437 s, 37%, to the tree's seal and the repository |
| One canonical edit costs about the size of the piece it re-summarizes, so a commit whose ops land many to a leaf costs about the square of them per leaf | hypothesis | confirmed if the time to replay n ops into one leaf's range grows as n², against linear for the same ops planted; refuted if it grows linearly | open |
| The replay is a pathological case for the tree implementation | opinion | Irakli, 2026-11-08 | - |
| Writing a transaction's nodes to a side file and copying the ones still reachable at commit would handle large transactions | opinion | Irakli, 2026-11-08 | - |
| Building each ordering bottom-up from sorted runs would write only finished nodes, never lifting one twice | opinion | the agent, 2026-11-08; the tree already does this for a commit into an empty tree (`plant`) | - |
