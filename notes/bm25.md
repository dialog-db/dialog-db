# BM25: concrete design

Detailed design for the phase-1 ranking index sketched in
`notes/search-indexing.md`. The goal is BM25 scoring where every stored
quantity is fact-local (so the region converges under merge and updates
incrementally) and every global quantity is an estimate read from `Scale`.

## The formula and where each variable comes from

```
score(q, e) = Σ_{t ∈ q}  idf(t) · tf·(k1+1) / (tf + k1·(1 − b + b·dl/avgdl))
idf(t)      = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
k1 = 1.2, b = 0.75
```

| Variable | Meaning | Source | Locality |
|---|---|---|---|
| `tf(t, e)` | occurrences of term in the document | posting payload, written at assert time | fact-local |
| `dl(e)` | document token count | posting payload (duplicated per term, small varint) | fact-local |
| `df(t)` | documents containing term | `Scale` estimate over the `(attr, t, *)` posting range | derived, no storage |
| `N` | documents with the attribute | `Scale` estimate over the `(attr, *)` AEV range | derived, no storage |
| `avgdl` | mean document length | estimated (see below) | derived |

Nothing global is ever stored, which is the whole trick: mutable corpus
counters are what make ranking indexes hostile to merge, and `Scale`
replaces them with range estimates read off index-node links without
descending. Both `df` and `N` drift upward together (consistent upper
bounds, ~1.13x realized), so their ratio — the only thing idf consumes —
is stable. Scores are computed at query time and never stored, so f64
platform variation is harmless.

`avgdl` has no scale-derived answer (scales count entries, not token
sums). Options, in order of preference:

1. Sample: scan a handful of leaves of the attribute's posting range,
   average the `dl` values seen, cache per root hash. Cheap, bounded,
   deterministic per root.
2. Running estimate over the postings the query streams anyway (biased
   toward query terms; acceptable).
3. A fixed constant per attribute as the v1 fallback.

## Storage: the posting region

New key tag (next free: `6`), a fourth ordering derived from string facts:

```
POSTING_KEY_TAG ‖ attribute ‖ term ‖ entity ‖ value_ref(32)
```

- `attribute`, `term`, `entity` in the escaped, 0x00-terminated byte-string
  encoding from `ordkey` (order-preserving, lossless).
- `term` is truncated to a fixed raw-byte budget (64 bytes, a `Manifest`
  constant) *before* escaping. This keeps posting keys far below
  `max_separator` (512) — long keys are demoted to rank 0 and can never be
  chunk boundaries, the unbounded-leaf pathology from
  `notes/boundary-policy-experiment.md`.
- `value_ref` is the value's 32-byte content hash (`Value::to_reference`,
  the same hash spilling already uses). It is the fact discriminator: a
  cardinality-many attribute can hold several string facts on one entity,
  and each fact must derive and retract its postings independently
  (fact-locality). Distinct values ⇒ distinct posting keys; the same value
  re-asserted collapses onto the same key, exactly as its EAV entry does.
  Deriving the discriminator from the value (not the `Cause`) matters:
  two initial assertions both have `cause: None` and would collide.
- Ordering consequence: within an `(attribute, term)` prefix, postings
  stream in **entity order**. That is what makes document-at-a-time
  scoring a k-way sorted merge rather than a hash join.

Why `attribute` before `term`: search is scoped per attribute (search
titles vs. bodies), ranges stay tight, and cross-attribute search is a
union the planner can see and cost. A global-term ordering can be added
later as another region if profiling demands it.

Payload reuses `Datum` following the blob-index precedent
(`BlobRecord` in `Datum::blob`):

```rust
struct PostingRecord { tf: u32 /* varint */, dl: u32 /* varint */ }
// v2 adds: positions: Vec<u32> for phrases + highlighting
```

encoded into `Datum::blob`. The posting's `Datum::version` carries the
**same `Version` as the source fact's claim** — this is what lets merge
screening treat postings mechanically like the data regions (below).

Posting keys get their own builder/parser in `key/posting.rs` (the blob
key precedent: a dedicated layout, not a forced fit into
`varkey::KeyParts`), plus a `Schema` arm in `TreeKey::schema`:
tag/attribute/term as `Dictionary` columns (heavy repetition within
leaves), entity/value_ref as `Arena`.

## Write path

All derivation lives in `write_instructions()`
(`dialog-artifacts/src/tree.rs`), next to the existing three-ordering
writes, inside the same `BufferedBatch`:

- **Assert** of a `String` value on an indexed attribute: analyze →
  `HashMap<term, tf>` + `dl` → one `(posting_key, State::Added(Datum))`
  per distinct term. The raw text is in hand here even when the value
  will spill.
- **Replace** (cardinality-one supersession): the existing supersession
  scan yields the old fact. Analyze old and new text, set-diff the term
  maps: vanished terms → `State::Removed`; changed `tf`/`dl` → rewrite;
  new terms → `State::Added`. The diff (rather than erase-all/write-all)
  avoids churning tree nodes for the unchanged majority of terms.
- **Retract**: re-derive terms from the retracted value → `Removed` per
  posting key. For a spilled old value this loads the archive block
  through the existing `SpillCache` — one block load per large-value
  retraction, the cost identified in `notes/search-indexing.md`.

Which attributes: v1 indexes **all `String` values** — deterministic, no
config surface, no non-fact-local dependence on config facts. Opt-in via
`dialog.index/*` facts can come later; it reuses the backfill machinery
below.

## Analyzer

v1: NFC normalization → UAX#29 word segmentation → lowercase (simple
case folding) → drop whitespace/punctuation-only tokens → truncate each
term to the raw-byte budget. `dl` = token count before truncation.

No stop-words (idf already discounts them; removal changes `dl`
semantics and adds config surface). No stemming in v1.

Determinism is a **format property**: replicas must derive byte-identical
postings from identical facts. The analyzer is identified by a version
constant in `Manifest` (folded into one format bump per
`notes/config-audit.md`, alongside the term byte budget and posting
format version). Unicode tables shift across crate releases, so the
segmentation/case-folding dependencies are pinned exactly, and any
upgrade is an analyzer version bump implying a region rebuild. Stemming
and language-specific analysis arrive only as such bumps.

## Statistics at the store boundary

A new store-boundary command alongside `Select` — `Estimate`: input a key
range, output a `Scale`-derived count bound. Implementation walks root
links, sums scales of links fully inside the range, and descends the two
partial boundary links a bounded number of levels for tightness. Cost:
a few node reads, no leaf scans.

Two rules inherited from `Scale`'s contract:

- **Advisory only.** Scales exclude ops pending in hitchhiker novelty
  buffers and are upper bounds besides. They may influence *scores* and
  *plan order*, never membership: no skipping a term's postings because
  its scale reads zero, no WAND-style pruning from scales. (Real
  max-score pruning needs stored per-term impact bounds — a later
  summary region, explicitly out of scope here.)
- Estimates read through the same provider layer and record demand like
  any read, so a subscription whose scores depend on them re-evaluates
  when the ranges change.

## Query surface

A new variant in `dialog-query`:

```rust
Proposition::Match(MatchQuery {
    attribute: Term<Attribute>,   // must be bound at plan time
    query: Term<String>,          // must be bound: the search string
    entity: Term<Entity>,         // binds matched documents
    score: Option<Term<f64>>,     // binds BM25 score
    limit: Option<usize>,         // top-k
    mode: Mode,                   // All (conjunctive) | Any (disjunctive)
})
```

- `estimate()`: from term `df` scales — min for `All`, sum for `Any` —
  so the greedy planner can order a `Match` against ordinary premises.
  This makes `Match` the first `Scale` consumer in `dialog-query`.
- `evaluate()`: analyze the query with the **tree's own manifest**
  analyzer version → per-term `(attr, term)` prefix ranges → cursors
  through the provider boundary → k-way merge on entity
  (document-at-a-time; postings are entity-ordered) → aggregate
  duplicates from cardinality-many facts per entity (sum `tf`, max `dl`)
  → BM25 → top-k heap when `limit` is set.
- Conjunctive fast path: order terms rarest-first by `df` estimate;
  v1 streams and merge-intersects, leapfrog seeks via narrowed selects
  can come later.
- Every read flows through the provider (`notes/tree-relations.md`
  invariant); the term ranges become the demand cover, so a standing
  `Match` subscription re-evaluates exactly when postings in those
  ranges change. `limit` makes `Match` non-monotone (a new document can
  evict a ranked one), which the DRed-style delete/re-derive path
  already accommodates: any demand-range hit re-runs the match.

Open decision: whether posting scans piggyback on `ArtifactSelector` (a
region discriminator + attribute/value-prefix reuse) or get a dedicated
command type next to `Select`. A dedicated command keeps the selector
honest; either way it must record demand.

## Merge, sync, replication

- `merge.rs`: add the posting tag to `tag_span` and screen the region
  with the same version-based observed-remove rules as the fact regions.
  Because a posting carries its source claim's `Version` and derivation
  is deterministic, "posting survives iff its source claim survives"
  falls out of applying identical screens to identical version sets.
  A `dialog-diagnose` check that the posting region equals
  `derive(fact regions)` guards the invariant.
- `spill.rs`: nothing to add — postings reference no out-of-tree blocks.
- Sync ships postings as ordinary novel nodes; history independence
  (identical facts ⇒ identical postings ⇒ identical chunks) gives
  structural sharing across branches and replicas.

## Backfill and format migration

Enabling the index on an existing tree is a format bump (manifest gains
analyzer version, term budget, posting version) plus a one-time
derivation pass: stream the AEV region, analyze each string fact, write
posting entries through `record()` in batches. The same machinery serves
later analyzer bumps and any future opt-in config change. Incremental
thereafter — no steady-state reindexing ever.

## Costs to measure first

One posting key per distinct term per fact: ~44 bytes of components +
32-byte value_ref before columnar compression (attribute and term are
dictionary columns; leaves within a term range compress hard). Expect
index-to-text size ratios near 1x and commit write amplification
proportional to distinct terms touched. Benchmark on the StackExchange
corpus (`notes/benchmark-dataset.md`, `se.post/body`) before layering
anything on: write amplification per commit, index size ratio, query
latency vs. a full-scan `Like` baseline, and subscription re-evaluation
cost under steady writes.

## Phasing

1. `key/posting.rs` (tag, builder/parser, schema arm), `PostingRecord`,
   manifest constants, ordering unit tests.
2. Derivation in `write_instructions` (assert/replace-diff/retract),
   merge region classification, diagnose invariant check, backfill.
3. `Estimate` at the store boundary over `Scale`.
4. `Match` proposition: planner integration, DAAT scorer, demand cover,
   subscription tests.
5. StackExchange benchmarks; then positions (highlighting, phrases),
   trigram region (fuzziness), stored impact bounds (pruning) as
   separate follow-ons.
